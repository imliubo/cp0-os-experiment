# Store 背景状态 v1

<!-- doc-locale: zh-CN -->
> [English](STORE-BACKGROUND-STATUS-V1.md) | **简体中文**

S7C 在用户离开 Store 页面后保持一个被接受的 Store 操作可见，并生成一个可信赖的完成通知。它不添加后台或自动更新策略：每次安装仍然始于明确的用户或操作员请求。

## 生命周期轮询

System Shell 启动后加载已安装应用注册表，并读取本地 Store Catalog。随后使用两种有界轮询频率：

- 在 Store 页面打开或执行 Store 操作的每一秒中；
- 在仓库闲置且另一个页面或应用处于前台时每五秒一次。

更快的路径遵循 `queued`, `downloading`, 和 `installing` 操作。
暂停、取消、失败或完成将在下一次权威目录响应时从活动状态中移除该操作。本地控制请求后的一小段时间延迟可以防止即时过时响应立即替换乐观接受状态。

轮询仅使用本地 Unix 域 Store 协议。搜索文本、应用程序活动和进度不会发送到网络。目录刷新仍然是显式的 Store 变动，不由后台状态路径执行。

## 状态栏

320x170 状态栏在屏幕标题和时钟之间保留一个固定区域。
它显示一个稳定的宽度标签：

| 权威操作 | 标签 |
| --- | --- |
| 下载中 | `DL 42%` |
| 安装中 | `INSTALL` |
| 排队中 | `QUEUE N` |

当一个串行批次包含多个条目时，活动计数包括所有排队、下载和安装的条目。代表状态使用优先下载，然后安装，然后排队，所以实际传输进度不会被后来排队的条目隐藏。暂停、取消、失败、可用、更新和已安装的应用程序不声明活跃状态。

标签是受信任的Shell表面的一部分，在Home、Tasks界面以及覆盖在不沉浸式前台应用的 compositor 模式暴露状态栏上时仍然可见。

## 完成身份

UI 保留守护进程的原始操作状态，与从 `available`, `update` 或 `installed` 派生的呈现状态分开。只有当连续两次验证的本地目录观察结果包含相同的应用 ID 和版本，并且其原始操作状态从未安装状态变为 `installed` 时，才记录完成。

首次成功的目录读取建立了一个基线，但从不创建通知。这防止了一个旧守护进程操作在Shell重启后产生虚假完成通知。保留原始状态也可以防止在Store报告完成之后的一个轮询周期内，由于appd安装版本注册表变得可见而导致的重复通知。

多个在通知前完成的应用可以聚合显示。一个完成命名为目录应用和版本；多个完成生成一个`N UPDATES INSTALLED`通知。应用名称和版本来自严格的Store响应，而通知标题和正文模板由Shell拥有。

权限和文档提示、电源和设置确认、现有通知和系统动作叠加优先显示。完成事件在可信叠加可以显示之前保持待处理状态。通知使用与应用程序通知相同的四秒横幅和 compositor 通知模式，而不授予应用程序 `notifications.post` 权限。

## 验证

UI行为测试涵盖活动优先级和数量，本地乐观状态，基线抑制，精确的ID/版本过渡绑定，聚合，事件一次触发，以及重复轮询去重。像素测试涵盖Store页面和Home页面在320x170分辨率下的进展，同时保持无关页面哈希不变。AArch64 compositor构建将最终的Shell链接起来，将警告视为错误。
