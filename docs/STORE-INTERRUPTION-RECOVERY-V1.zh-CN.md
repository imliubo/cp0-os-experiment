# Store 中断恢复 v1

<!-- doc-locale: zh-CN -->
> [English](STORE-INTERRUPTION-RECOVERY-V1.md) | **简体中文**

S7E 在 Store 安装的每个持久化边界定义了恢复过程。恢复过程从不信任进程内存、客户端提供的部分文件名或模棱两可的 appd 响应。重试总是从新的 S7D 预检开始，并重复执行策略、容量、Catalog、包和 appd 验证。

## 下载和断电

包片段保持私有 `0600` 正常文件，仅通过签名的包 SHA-256 命名。守护进程重启没有持久化的队列、下载、安装或同意状态。因此，Shell 返回到目录的权威可用/更新状态，并且新的显式安装只能重用相同签名摘要下找到的字节。

中断写入可能会留下任何前缀长度，包括零或完整的声明大小。下载器会在传输前对这个长度进行限制。较短的响应仍然是网络失败，并保留了限制的前缀。如果部分大小超过声明大小，则会在重新传输前截断。完整的文件在移交前总是会被重新哈希，因此断裂或损坏的前缀只能导致验证失败，而不会导致安装失败。

## HTTP恢复

对于非空的部分，客户端使用身份编码请求 `Range: bytes=N-`。响应 `206` 必须包含精确的 Content-Range: bytes N-(total-1)/total；缺少、损坏、错位、插入或总长度不同的头部在响应字节附加前被拒绝。其他非成功状态是网络失败。

服务器可以忽略 Range 并返回 `200`。在这种情况下，客户端截断旧前缀并从字节零消费响应。这是安全的，但会损失恢复效率。每个响应仍然受限于带符号的包大小，并且最终的 SHA-256 校验不变。

## 摘要校验失败

大小和SHA-256在appd移交前立即从暂存的部分中进行检查。摘要不匹配会立即截断部分文件为零，并报告关闭的`verification`失败原因。不会创建移交文件，并且稍后的显式重试会从零开始下载。截断失败仍然是一个验证失败，不能继续进行到appd。

## 向 appd 交接

`cp0-stored` 复制一个经过验证的包到一个私有的、生成的
`store-PID-SEQUENCE.capp` 文件同步后发送给 appd 一个包含目录绑定、所有者、App ID、版本、摘要和字节计数的catalog。正常响应或报告的失败会移除移交文件。

模棱两可的情况是 appd 在其连接到 `cp0-stored` 关闭之前提交了原子安装。因此，重试确切安装版本是一个幂等重放，而不是降级：appd 仍然会重新检查文件所有权、长度、SHA-256、Store 签名、清单标识、SDK 兼容性和确切安装的树结构，然后再返回成功。较低版本和相同版本但不同内容仍然是冲突。重放不会改变安装时间和回滚历史，并且即使恢复的应用程序已经启动也会被接受。

在守护进程启动时，`cp0-stored` 验证专用移交目录是私有的，并且由其有效 UID 所拥有。它仅移除严格的生成移交名称。未知文件将被保留，而生成看起来的目录将在启动时失败而不是触发递归删除。失败的暂存复制也会立即移除其不完整的目标。

## 验证

确定性测试覆盖：

- 一个由新Store服务实例消费的摘要绑定部分；
- 一个中间响应的网络断开连接，随后重启并使用精确前缀重用；
- 一个真实的回环 HTTP `206` 范围错误在追加前被拒绝，然后是一个正确的范围完成相同的部分；
- 错误的完整字节截断为零，没有安装程序调用，和一次干净的重试；
- appd 提交后跟随连接丢失和一个精确的幂等重放；
- 保留无关收件箱条目的受限启动清理；
- 精确重放，严格升级、降级以及无效版本决策在 appd 中。

CM0门在稳定性观察窗口之后，重复这些行为与生产HTTPS源和systemd服务。物理断电、链接移除、appd杀进程时间、LCD进度、安装的注册表状态以及SD文件系统证据仍然是S9artifacts；本地进程测试不能替代这些硬件结果。
