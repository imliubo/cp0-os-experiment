# Phase 3C: 权限决策和可信提示

<!-- doc-locale: zh-CN -->
> [English](PHASE3C-PERMISSIONS.md) | **简体中文**

## 安全模型

应用程序在验证过的清单中声明能力和用户可见的原因。运行时或代理从不通过权威声明提供应用程序ID。代理将从受信任的运行时通道识别其调用者，并通过`appd`的根拥有的安装注册表解析规范清单。

权限数据库是 `/var/lib/cardputerzero/registry/permissions.json`。它是严格的 JSON 格式，包含模式版本、稳定的应用程序 ID 和每个能力的决策。`appd` 拒绝符号链接、非常规文件、非根所有权和可被组或其他人写的文件。持久更改使用模式 `0600` 临时文件，`fsync`，原子重命名和父目录 `fsync`。

未声明的能力总是被拒绝。声明的能力如果没有存储的决策则创建一个受信任的提示。决策具有以下语义：

- `allow-once` 只存在于 `appd` 内存中，并在应用停止时被清除；
- `allow-always` 被持久化；
- `deny` 被保存并移除任何会话授权。

## 提示状态机

只有一个提示可以待命，因为系统只有一个前台应用。
重复请求相同的应用和能力返回相同的提示。不同的请求被视为忙，直到当前提示被解决或应用停止。提示ID是非零的，过时的ID不能修改决策。

提示显示元数据仅来自标准安装的manifest：提示ID、应用ID、应用名称、能力和声明的原因。这防止了不可信的请求载荷冒充另一个应用或改变System Shell显示的文本。

## Shell 控制 合约

经过身份验证的 appd 协议增加：

- `get-permission-prompt` 以检索任何待处理的提示；
- `resolve-permission` 带有提示 ID 和 `allow-once`, `allow-always` 或 `deny`.

现有的套接字 DAC 和 `SO_PEERCRED` 检查限制了所有命令仅对 root 和 `cp0-shell`。诊断等效项为：

```sh
cp0ctl permission pending
cp0ctl permission resolve <prompt-id> once|always|deny
cp0ctl permission reset <app-id> <capability>
```

`reset` 只限制在认证的控制套接字上。它通过相同的原子持久路径同时移除一个会话授权和一个存储的决策，因此下一个能力使用会再次提示。它拒绝与匹配的待处理提示进行竞争。

生产系统的Shell暴露相同的操作而不授予通用控制通道。打开**应用**，选择一个应用程序，打开其详细视图并切换到**权限**页面。每个声明的能力显示为其中之一：

- `ASK`: 没有决策被存储；下一个能力请求会打开可信提示。
- `ALLOW`: 当前有一个会话或持久授权生效；
- `DENY`: 当前存在一个持续的拒绝。
- `POLICY`: 设备策略拒绝该能力，且所有者无法从应用页面对其进行覆盖。

按下 `ALLOW` 或 `DENY` 会将该能力重置为 `ASK`。它从不默默地授予被拒绝的能力。应用程序必须再次请求该能力，之后受信任的提示将提供 `ONCE`、`ALWAYS` 和 `DENY`。`ASK` 和 `POLICY` 行是只读的。

此阶段不暴露通用应用权限套接字。能力请求通过类型化的代理服务进入。通知代理服务是第一个集成目标；硬件代理服务和文档代理服务将重用相同的状态机，而不获得生命周期或权限管理的权限。
