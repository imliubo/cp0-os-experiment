# 多任务架构

<!-- doc-locale: zh-CN -->
> [English](MULTITASKING-ARCHITECTURE.md) | **简体中文**

## 产品合同

CardputerZero 系统保持为单前台系统。恰好一个应用可以拥有 320x170 的应用层和键盘焦点。按下 F3 可打开一个可信任的任务切换器，最多包含十个任务卡片；选择一个卡片将激活该任务而不是启动第二个实例。

一个应用最多只有一个任务。启动第十一项不同的应用会驱逐创建序列最小的任务，即使另一个任务使用得不那么频繁。在终止前，appd 会请求应用提供一个有界、版本化的检查点。超时、不支持的回调或无效的Blob记录下来但永远不会阻止终止。被容量驱逐的任务会从F3中消失；它的检查点保留在应用的私有状态中，并在应用下次从启动器打开时提供。

十任务限制是一个产品限制，而不是承诺在512 MB CM0. appd 下 WAMR 进程总是保持驻留的保证。在内存压力下，appd 可能会冻结后台任务或将它们检查点保存并销毁其进程，同时保持它们的卡在 F3。

## 任务状态

| 状态 | 进程 | 应用代码运行 | 表面 | 激活 |
| --- | --- | --- | --- | --- |
| `foreground` | 居住 | 是 | 活动或被Shell覆盖 | 直接 |
| `background` | 常驻 | 是，优先级降低 | 隐藏 | 直接 |
| `frozen` | 居住 | 否 | 最后一帧保留 | 解冻，然后直接 |
| `checkpointed` | 缺失 | 没有 | 可信的最后一帧保留 | 启动并恢复 |
| `crashed` | 缺失 | 没有 | 可信的最后一帧加上崩溃标志 | 清洁启动或恢复 |

按下 F3 会把键盘焦点切换到 System Shell，但不改变逻辑前台 task。这样每次打开可信 overlay 时不会产生虚假的前台转换；切换卡片才会改变前台 task。

每个任务都有非零且单调分配的 `task_id`、不可变的创建 sequence，以及单调更新的激活
sequence。创建 sequence 决定 FIFO 容量淘汰，激活 sequence 决定界面上的最近使用优先
卡片顺序。墙钟时间和 compositor token 都不作为持久身份。

## 所有权

### 前台应用

appd 是生命周期管理方。它的任务注册表拥有任务身份、状态、运行时单元绑定、前台选择和驱逐顺序。所有修改操作都由一个生命周期协调器序列化。缓慢的 systemd、检查点和 compositor 操作作为有界步骤运行，在提交前重新验证预期的任务 ID 和运行时生成。

现有的单个`Option<RuntimeSession>`变为任务索引化的运行时映射。每个运行时监视器与其任务ID和生成相关联，因此旧的监视器不能将重启的任务标记为崩溃。权限提示、文档提示和媒体动作也使用前台任务ID而不是全局单个运行时槽。

### 前台应用运行时

每个居民任务保留其现有的专用UID，临时systemd单元、cgroup和bubblewrap/WAMR沙盒。后台执行不会削弱隔离。appd通过systemd更改调度属性；应用程序不接收进程或cgroup控制API。

启动合同添加了 `CP0_TASK_ID` 和一个预先打开的身份验证运行时控制通道。运行时将其任务 ID 和生成信息报告给 appd，并使用私有 compositor 协议将生成的 Wayland 表面绑定到该身份。`xdg_toplevel.app_id` 保持为不受信任的显示文本。

### compositor

compositor 继续强制只有一个普通应用层和一个键盘焦点，同时可保留多个隐藏应用视图。可信 surface record 以 `(task_id, runtime_generation)` 为 key，并使用仅供 System Shell 使用的易失性 compositor token。token 永不持久化。

compositor 从应用最后提交的 buffer 捕获缩略图；
应用程序不能提交自己的任务切换器图像。捕获输出是RGB565格式，分辨率为160x85（27,200字节）。十个图像最多消耗272,000字节加上少量元数据。只为选定的卡分配双缓冲区，而不是为每个任务分配。

在 F3 可见且驻留且未冻结的情况下，表面可以每 2 Hz 更新其缓存的缩略图。冻结、检查点和崩溃的任务显示其最后受信任的帧。Shell 从不直接映射应用程序缓冲区； compositor 将其复制到一个密封的只读共享内存对象，并用任务 ID、运行时生成和缩略图生成进行标记。

### System Shell

System Shell 从 appd 获取任务元数据，并从私有 compositor 协议获取表面/缩略图句柄。它只依据可信的 task ID 和 Runtime generation 合并这些来源。未匹配的 compositor 表面不会显示为卡片；没有当前缩略图的任务使用 System Shell 自有的占位图。

F3 显示一个可水平滑动的卡片堆栈，大小为 320x170。左键和右键切换选中的卡片，上键和下键选择其 OPEN 或 STOP 动作，回车执行所选动作，空格键直接停止它，Esc 或 Home 键返回 Home。每当 F3 打开或选中的卡片改变时，OPEN 会被选中，以防止意外的回车终止任务。只有中间的卡片使用完整的 160x85 缩略图；相邻的卡片部分可见，以便于导航发现。卡片分配是固定的，因此标签、徽章和缩略图不会改变布局。

## 生命周期交易

### 启动一个新的应用

1. appd 拒绝第二个实例并检查启动策略。
2. 如果存在十个任务，appd 会捕获最古老任务的最新可信帧，并请求一个严格超时的检查点。
3. appd 停止受害单元，保存净化后的检查点结果，并移除受害任务。
4. appd 用新鲜的运行时生成和任务 ID 启动一个新的沙盒。
5. 在Runtime和compositor身份绑定之后，appd将旧的前台应用后台化，并提交新的前台任务。
6. Shell 接收新任务生成并激活匹配的 compositor 令牌。

任何在第三步之前失败都会保留旧的任务注册表。检查点失败不是事务失败。在驱逐后如果启动失败，会保留驱逐记录并返回到主页；它不会复活一个部分停止的进程。

### 切换任务

1. Shell 将 `activate-task(task_id)` 发送到 appd。
2. appd 解冻一个冻结的任务或启动并恢复一个检查点任务。
3. appd 从上一个任务撤销前台专用资源，更新调度权重并提交前台过渡。
4. appd 返回预期的运行时版本。
5. Shell 使用相同的受信任配对激活 compositor 令牌。

如果任何身份或 generation 检查失败，compositor 会停留在可信 Shell。绝不会出现两个应用同时可见或同时获得焦点的时刻。

### 关闭并崩溃

关闭卡片是一个明确的停止操作，会移除其任务记录。它不会删除私有应用程序数据或之前持久化的检查点。意外的单元退出只会将匹配的运行时生成更改为`crashed`，清除会话范围内的权限并释放独占资源。

## 检查点 SDK 合同

检查点是可选的，并由应用程序定义。它不是WASM内存转储。
下一个SDK ABI增加了一般的导出回调，用于检查点和恢复，由Rust和C SDK包裹：

- schema 版本是一个应用程序拥有的非零 `u32`；
- payload 是不透明的，并且限制在 8 KiB 内；
- 检查点执行有一个250 ms的墙时间超时和一个燃料预算；
- 恢复运行在第一个可见帧之前，并具有相同的边界；
- Runtime 在返回控制之前验证指针并复制字节；
- appd 通过经过身份验证的私有存储代理在预留的密钥下存储 blob；该密钥对正常 SDK 存储调用不可用；
- 检查点元数据包括应用ID、包版本、方案版本、长度和SHA-256；只有当应用显式声明兼容性时才提供版本不匹配。

应用程序即使不实现回调也仍然参与多任务处理，但在容量驱逐或进程回收后从干净的启动状态恢复。

## 资源策略

前台应用使用当前的CPU和内存限制。后台应用获得较低的CPU权重，并且会失去摄像头、麦克风、GPIO输出以及其他独占租约，除非特定能力的策略明确允许继续。网络和音频播放可以在获得权限后继续。当任务离开前台时，权限和文档提示会被取消或推迟显示；它们永远不会被归因于不同的前台任务。

第一个实现使用了这些压力阶段：

1. 在内存余量健康时，保持后台任务驻留；
2. 冻结最不最近激活的后台任务；
3. 检查点和停止冻结的任务，同时保留其任务卡片；
4. 允许内核/系统单元限制仅在最终失败时终止一个任务，然后标记该任务 `crashed`。

精确的压力阈值需要设备测量，并且在模拟开发过程中故意没有硬编码。

## 协议更改

appd 协议 v2 添加了 `list-tasks`, `activate-task` 和 `close-task`. 任务行包含任务 ID, 可信应用元数据, 状态, 创建和激活序列, 检查点可用性, 运行时生成和缩略图生成。现有 `start` 仍然是启动器操作：它激活一个现有任务或创建一个任务。现有 `stop` 用于关闭任务以保持兼容性。

私有 System Shell Wayland 协议 v7 增加 compositor 认证的 App UID 事件，用于 simulator slice。Runtime 认证的 task/generation 绑定和 sealed thumbnail 事件仍用于 MT3/MT4。协议版本协商仍然严格；镜像和设备发布必须把 appd、System Shell 和 compositor 作为一个 bundle 更新。

## 模拟实现状态

`codex/multitasking-main-integration` 分支整合了以模拟器为先的主线切片，但尚未部署到设备：

- appd 协议 v2 及其 C 客户端暴露任务列表、激活和关闭功能；
- `TaskRegistry` 强制一个前台任务，十任务绑定，独立的 FIFO/MRU 序列，生成安全的崩溃处理和版本化的快照；
- 服务器在意图过渡期间保留多个 Runtime 会话，并不再销毁发送者。
- F3 渲染固定的 160x85 卡堆栈，包括可信的 RGB565 测试帧、占位符以及所有五个生命周期状态；
- Wayland 协议 v7 报告内核认证的客户端 UID。由于此版本只允许每个 App UID 一个任务，Shell 将 appd 账户 UID 加入到该表面。App-id 文本从未被信任。后续的多实例版本必须添加一个 Runtime 认证的 `(task_id, runtime_generation)` 绑定；
- `TaskJournal` 原子地存储验证过的注册表快照和一个64项容量-驱逐历史。重启 reconciliation 保留活动的代并标记缺失的单元为崩溃状态；
- `CheckpointBlob` 强制执行 8 KiB、模式、包、SHA-256 和 250 ms 的模拟合约。SDK 暴露了一个可选的生命周期世界和稳定的 C 导出签名；
- `ThumbnailCache` 拒绝 UID/任务/运行时/代际不匹配，限制更新速率到每 2 秒 1 次，并证明十帧 272,000 字节的预算；
- 资源管理器从抽象的压力级别生成确定性的CPU、冻结、检查点/停止和租约撤销计划。在测量之前不猜测CM0阈值。
- 与最新 Setup、Developer Access、Store 和电源UI的集成保持
  `struct cp0_ui` 低于其64 KiB的限制，通过分配一个固定的880字节任务表进行分配；拆卸时会显式释放它；
- 非幂等的包安装、升级、回滚和卸载会拒绝所有活动的逻辑任务，包括检查点/崩溃任务且无驻留进程；精确版本的Store重放仍然是幂等的。
- 当同一个 App UID 有多个临时表面存在时，Shell 会优先选择最近宣布的令牌。在生产发布前仍需要 Runtime 生成绑定。

任务日志、检查点信封、缩略图缓存和调节器是该阶段的模型组件。量产布线仍然需要经过认证的Runtime控制套接字、compositor memfd捕获、systemd日志记录挂钩和测量压力阈值。这些故意保留在设备集成门之后，而不是部分部署。

## 交付路线图

1. MT0 架构和不变量 - 完成。协议、状态所有权、限制、FIFO 语义和故障行为已规定并进行了模型测试。
2. MT1 appd 和 F3 模拟 - 完成。多会话 appd，协议 v2，UID 绑定激活和卡 UI 编译针对 ARM64。
3. MT2 持久化和 SDK 检查点模型 - 完成。原子任务日志，
重启一致性检查，边界 Blob 和可选 SDK 生命周期 ABI 本地测试已完成。
4. MT3 可信捕获集成 - 待设备门。将 compositor 捕获添加到密封的只读 memfd 对象中，并将其连接到 Shell，而不映射 App 所有的内存。
5. MT4 运行时生命周期集成 - 待命设备门。添加私有控制套接字，WAMR 回调燃料/截止日期强制执行，原子检查点代理命名空间和在首帧前恢复行为。
6. MT5 测量管理器 - 待处理设备门。测量 CM0 内存/CPU/SD 行为，选择阈值，调整冻结/检查点顺序并运行断电恢复测试。
7. MT6 发行接受 - 待授权。部署一个捆绑包，
验证 F3 与 0/1/3/10 个应用，锻炼第 11 个应用的 FIFO 路径，重启 appd，
验证检查点持久性，然后仅在请求时打包一个新镜像。

## 模拟和接受

此阶段无需进行任何硬件操作。本地接受必须覆盖：

- 随机启动、切换、冻结、检查点保存、崩溃和关闭序列中的一个前台任务；
- 启动时的十个任务硬限制和严格的FIFO淘汰机制 11;
- 检查点超时仍然会驱除受害者；
- stale task/Runtime/thumbnail generation 按 fail-closed 原则拒绝；
- 最近使用顺序的视觉排列不会改变先进先出创建顺序；
- F3 像素快照在零、一、三和十张卡时；
- 键盘导航，激活和关闭事件；
- 强制进程重建下的模拟器检查点/恢复
- 固定缩略图内存和帧率预算。

设备部署、服务重启和镜像生成仍超出范围，直到明确授权。

Developer Mode 不是系统组件热更新通道。兼容的多任务 system bundle 就位后，它可以安装和测试已签名 SDK 应用，但不能替换 appd、System Shell、compositor policy 或 Runtime。因此当前真机工作仍需使用协调的 bundle 加重启，或由设备所有者协助烧录新镜像。
