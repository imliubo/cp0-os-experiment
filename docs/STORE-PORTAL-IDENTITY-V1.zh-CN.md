# Store Portal Identity v1

<!-- doc-locale: zh-CN -->
> [English](STORE-PORTAL-IDENTITY-V1.md) | **简体中文**

## 边界

开发者门户是一个浏览器应用，后面有一个专用的BFF。BFF 是唯一参与外部OpenID Connect的组件，也是唯一接收浏览器会话cookie的组件。Store 控制服务仍然是一个私有的OAuth资源服务器。浏览器从不接收Store控制令牌、OIDC刷新令牌、邀请摘要或外部OIDC主题。

v1 合约是提供者中立的。生产配置必须提供精确的发行者白名单、客户端注册信息、重定向 URI、接受的 MFA ACR 值、签名算法和时间偏差限制。授权码配以 PKCE、状态和nonce 是强制性的。隐式授权和密码授权不受支持。

## 身份模型

一个账户是一个稳定的Store主语，一个团队成员资格是一个单独的、版本化的授权关系。外部身份链接将一个精确的大小写敏感的`(issuer, subject)`配对映射到一个账户。电子邮件是验证联系和邀请路由的数据；它永远不能作为登录密钥，并且不能更改身份映射。

一个账户最多可以有八个活跃的外部身份链接。添加或删除一个链接需要一个新的提供方挑战。最后一个链接不能被删除。如果另一个账户已经拥有该链接，则不能通过门户将其合并。账户合并和恢复升级需要离线支持程序，并且需要双重控制，这些功能在v1之外。

一个账号可以在最多八个团队中拥有活跃会员身份。每个会员身份保留其现有的全局唯一`member_id`；一个`account_id`将这些授权主体绑定在一起，而不改变应用、审计或访问令牌的所有权。
前端框架（BFF）选择一个活跃的会员身份，并通过私人受众绑定的交换获得一个短期控制令牌。它永远不会将该令牌转发给浏览器。暂停和删除的会员身份无法被选择或交换。

浏览器面对的API从不返回`subject`。它只暴露一个配置的提供者标签、一个稳定的不透明链接ID、链接时间以及链接是否用于当前会话。

## 浏览器会话

回调成功后，BFF 创建一个随机的256位不透明会话密钥，并仅存储其SHA-256摘要。浏览器接收它作为`__Host-cp0_portal`，带有`Secure`、`HttpOnly`、`SameSite=Strict`、`Path=/`，没有`Domain`。会话的闲置生命周期为30分钟，绝对生命周期为八小时。身份验证、权限变更和MFA步骤更新密钥；注销和成员资格暂停/删除撤销它。

每次状态变更的 JSON 请求还需要：

- 精确允许的 `Origin` 和同源获取元数据；
- `X-CSRF-Token` 中每个会话的随机同步值;
- 一个随机的`Idempotency-Key`绑定到账户、操作和请求摘要；
- `If-Match` 对于每个版本化的团队，邀请或身份链接的变更。

CSRF值可能由`GET /portal/v1/session`返回；它不是一个身份验证凭据。它存储为摘要，并随着会话一起轮换。CORS被禁用。响应使用`Cache-Control: no-store`和一个防止回调和邀请材料泄露的referrer策略。

会话只在签名、颁发者、受众、随机数和配置的ACR验证之后记录提供者`auth_time`。敏感操作要求时间不超过五分钟。会话创建时间本身不是MFA证明。

## 邀请生命周期

只有当前团队所有者，拥有 `store.teams.write`，启用 MFA 并完成一步提升，才能创建或取消邀请。邀请角色正好是 `developer`、`release-manager` 或 `viewer`；所有者故意被排除在外，并必须通过现有的保护角色变更端点另行授予。

BFF 生成一个256位的邀请密钥，只存储其摘要，并通过配置的事务邮件工作者发送原始值。API 响应、审计事件或通用外箱负载都不包含原始密钥。接受 URL 将密钥放在片段中。门户将其放在有界 JSON 负载中发送到 `invitations:inspect` 或 `invitations:accept`；它从不将密钥放在请求路径、查询字符串、日志或referrer中。

邀请在七天后失效，并遵循一个终端过渡：

```text
pending -> accepted
pending -> cancelled
pending -> expired
```

接受需要一个活跃的门户会话，并且该会话的提供者验证电子邮件等于规范化邀请地址。它会原子地创建成员资格，推进团队版本，标记邀请已被接受，并附加审计和出箱事件。被移除的成员资格永远不会重新激活；重新邀请需要一个单独版本的成员资格标识设计。精确的接受重放是幂等的，而另一个账户在过期后或取消后使用则会失败。

每个Team中的待处理邀请和活跃/暂停成员总数不得超过100。
创建受每Team的速率限制影响，并在数据库工作前对电子邮件进行标准化。
生产交付退信处理和滥用阈值是部署策略，但只能取消待处理邀请，而不能更改成员身份。

邀请的创建、取消和接受都会锁定并推进团队聚合恰好向前一步。它们的`If-Match`先决条件和响应`ETag`因此总是引用团队版本。邀请也有自己的单调`resource_version`，与`team_resource_version`一起返回，但这个子版本从不被加载到HTTP`ETag`头中。

## 持久性和事务

PostgreSQL 适配器使用五张身份表：

| 表格 | 安全不变式 |
| --- | --- |
| `portal_accounts` | 稳定ID；联系变更会版本化，从不作为身份使用 |
| `external_identity_links` | 不可变发行者/主题所有权；无物理删除 |
| `portal_sessions` | 仅秘密和CSRF摘要；单向撤销和有限的有效期 |
| `oidc_login_transactions` | 哈希状态/nonce/验证器，精确意图和短有效期 |
| `team_invitations` | 只有令牌摘要；不可变目标/角色和终端状态机 |

邀请接受，团队/成员创建，会话旋转，
幂等完成，审计和出箱追加在一个 `SERIALIZABLE`
事务中发生。OIDC令牌交换和电子邮件交付在数据库事务之外。短数据库租约和去重ID连接这些副作用；重试不能创建另一个团队或发送不同的邀请密钥。

门户 BFF 不持有签名或 Store 发布密钥，也不能授予审核员或操作员角色。审核员工作流 SSO 仍然是一个单独的发行人、客户端、cookie 命名空间和服务边界。

## API和交付阶段

浏览器合同在 `schemas/store-portal-identity-v1.openapi.json` 被冻结。重定向端点启动或完成 OIDC；JSON 端点涵盖当前会话、链接管理和邀请生命周期。错误主体使用封闭的 Problem 形状，并且从不反映提供者令牌、主题、邀请值或数据库细节。

实施过程分为四个验收切片：

1. [完成] PostgreSQL 身份验证、OIDC 交易和会话状态机
   以及 SQL 跳过测试；
2. [完成]通用OIDC授权码+PKCE回调，cookie/CSRF
   强制执行，轮转，空闲/绝对过期和注销；
3. [完成] 邀请创建/列表/检查/取消/接受，通过电子邮件-工人
   交接，精确重放，团队限制和事务回滚测试；
4. [in progress] Portal BFF/浏览器集成、两个提供商的链接/取消链接、恢复测试、会话盗用遏制和会员暂停/移除传播已完成；生产IdP符合性仍处于外部状态。

生产登录在配置的发行人、接受的MFA保证、电子邮件交付、账户恢复、滥用响应和隐私保留策略通过其外部审核之前仍被禁用。
