# Store 发行者，目录构建者和透明度提交者

<!-- doc-locale: zh-CN -->
> [English](STORE-PUBLISHER.md) | **简体中文**

S5G 添加了 `cp0-store-publisher`，这是唯一一个允许读取 Store Ed25519 私钥的参考进程。它消费 Release 控制面事件，重新验证已批准的不可变内容，Store 签名包，构建一个确定性签名目录，并发布不可变静态源的版本。它是一个后台服务，永远不会包含在 CardputerZero 设备镜像中。S5H 为每个目录快照扩展了相同的隔离提交边界，并附加一个只读透明叶和签名检查点。

## 信任边界

控制服务器、开发者门户和审查控制台从未接收私钥。参考签名器接受一个原始的32字节Ed25519密钥，来自一个绝对、不跟随、普通文件，且模式为`0600`或更严格。这是一个紧密隔离的文件-密钥实现，用于开发和受控部署；它不声称生产HSM集成或替代生产密钥仪式。

在签名之前，发布者从不可变的内容寻址片段中重构每个提交部分。它验证片段的连续性、大小和SHA-256，每个完整部分的摘要以及最终提交内容的摘要。然后，它解码开发者的`.capp`，验证其签名是否与App团队当前有效的密钥匹配，拒绝现有的Store签名，并重新解析清单和Store列表。包、清单、永久App注册表、发布、默认区域和批准的资产必须完全一致。

S6A 使生产快照严格遵循发现目录 v2。发布者还会读取所有者团队名称和批准的默认列表本地化，然后将开发者、副标题、类别、关键词、年龄分级和隐私/支持网址签署到每个条目中。目录 v1 仍然接受用于离线恢复组件，但 v1/v2 字段不能混合。如果升级后的投影仍然包含遗留组件，完整的快照将保持为纯 v1，直到所有包含的组件都具有完整的签署发现数据为止。请参阅 `STORE-DISCOVERY-CATALOG-V2.md`。

S6B 添加了 Catalog v3 媒体描述符。发布者在与 Store 签名包相同不变的生成中写入固定服务器衍生的图标、屏幕截图和详细信息路径。根 Catalog 绑定图标/详细信息哈希，而绑定的详细信息文档绑定每个屏幕截图。迁移选择完整的 v1、v2 或 v3 投影；方案字段永远不会混合。参见`STORE-MEDIA-RESOURCES-V1.md`。

S6E 添加了一个向后兼容的带签名的根索引。投影仅使用 v1-v4 `SignedCatalog`，前提是它最多有 64 个应用程序且其编码字节符合 48 KiB 的限制。否则，发布者会确定性地将应用程序打包成独立签名、大小测试过的碎片。带签名的根将每个碎片描述符、确切类别索引和任何 v4 编辑投影绑定在一起。参见 `STORE-SHARDED-CATALOG-V1.md`。

## 队列和序列模型

`release.publish-requested` 和 `catalog.rebuild-requested` 的出箱记录被实现为租赁的 `store_publication_jobs`。PostgreSQL 验证每个任务都匹配其源事件。只有一个任务可以被 `running`；其首次声明将单例目录计数器向前推进恰好一个单位，并永久保留：

- 一个永不重复的全局Catalog序列；
- 确定性发布和过期时间戳；
- 源发布状态和资源版本；
- App 所有者团队的验证开发者显示名称。

开发者的名称在首次声明时原子性地冻结，后续的SQL更新无法更改。因此，团队重命名在写入后的一代之前不会改变。重试保留所有预留输入，因此它们产生相同的带符号字节。过期的租约通过尝试七重新入队。尝试八，无效的批准源或撤销的开发者密钥结束任务。初始发布原子性地将`publishing`推进到`published`或`publish-failed`；目录重建失败时，保留的发布状态不会改变。

一个控制事件在发布前被取代会消耗其预留的序列号而不创建快照。这种故意的间隙防止了序列号的重复使用。最新的事件将构建当前状态。审计和出箱记录区分已发布的、失败的和被取代的结果。

## 目录投影

每个成功由Store签名的软件包都有一个只读记录和一个不可变路径：

```text
generations/<initial-sequence>/packages/<release-id>.capp
```

对于每个应用，构建者选择具有最大现有包发布序列的发布版本。`published` 包含该发布版本，而 `paused` 或 `removed` 不包含该应用且不会回退到较旧版本。一个新的 `publishing` 目标暂时保留序列并取代较旧版本，直到其目录被构建。暂停、恢复和删除每个请求都会请求一个新的全局快照，但保留发布版本的原始包序列。

目录中的应用程序按 App ID 排序。遗留根限制为 64 个应用程序和 48 KiB；索引生成限制为每片 16 个碎片、64 个应用程序和每片 48 KiB，总计 1024 个应用程序。默认列表本地化提供签名名称和摘要；清单权限在编码前进行排序。PostgreSQL 使用追加只读元数据存储精确的签名根和碎片字节。

## 文件系统提交和恢复

发布者不能原子地提交 PostgreSQL 和静态文件系统。因此，它使用这种顺序：

1. 在 PostgreSQL 中保留序列和时间戳；
2. 构建确定性签名的制品；
3. 写入、同步并原子重命名包含目录根、任何碎片、透明度叶/检查点和Store公钥的不可变版本；
4. 原子提交包元数据，Catalog快照，透明记录，
发布状态，审计和出箱；
5. 验证每个提交的生成对象，并原子性地切换 `current`.

在步骤4之前发生崩溃会留下一个未引用的代，该代通过相同的租赁任务被验证和重用。在步骤4之后发生崩溃会暂时使先前的目录可见；启动时会验证完整的数据库透明历史记录，然后逐字节检查最高目录、每个绑定的分片、叶子、检查点和公钥，在此之后修复`current`。没有快照的数据库会拒绝任何预存的`current`指针，而不是暴露未提交的内容。该过程从不重写或删除已提交的代。

透明协议、完整前缀验证器、迁移行为和明确限制在 `STORE-TRANSPARENCY.md` 中有文档说明。

## 隔离配置

`crates/cp0-store-publisher/systemd/cp0-store-publisher.service` 作为一个专用账户运行，没有 IP 网络命名空间、设备、能力、家目录访问或可执行的可写内存。它仅接收通过 Unix 套接字的 PostgreSQL，只读提交对象和密钥，以及一个可写的原点根目录。生产数据库角色必须仅限于发布队列、所需读模型、发布完成、不可变制品、审计和出箱。

所需的环境变量在 `crates/cp0-store-publisher/systemd/store-publisher.env.example` 中文档化。
